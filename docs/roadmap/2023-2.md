## Projeto #2 — Sniffer

**Matéria:** Redes I
**Impacto:** 🔴 Alto
**Categoria:** Vídeo
**Esforço:** 2 semanas

### Objetivo

Sniffer de pacotes em Python (Scapy) com análise automatizada para detecção de:

- **Port scanning** — tráfego de 1 origem para múltiplas portas de 1 destino em curto intervalo
- **ARP spoofing** — mensagens ARP inconsistentes na mesma LAN
- **DNS tunneling** — queries DNS anormalmente longas ou com alta entropia no subdomínio
- **Beaconing** — conexões periódicas (intervalo constante) para o mesmo destino

### Stack

| Captura                          | Python 3.11 + Scapy |
| API                              | FastAPI             |
| UI visualização                  | Next.js + Recharts  |
| Armazenamento (análise de PCAPs) | SQLite embarcado    |

### Passo a passo

**Semana 1 — Motor Python**

Dia 1-2: Setup do ambiente Python, primeiro detector (port scan) com TDD usando PCAPs sintéticos gerados com Scapy:

```python
# tests/test_port_scan.py
from scapy.all import IP, TCP, Ether, wrpcap, rdpcap
from pathlib import Path

def generate_port_scan_pcap(tmp_path: Path) -> Path:
    packets = [
        Ether()/IP(src="10.0.0.5", dst="10.0.0.10")/TCP(dport=port, flags="S")
        for port in range(1, 1001)
    ]
    path = tmp_path / "scan.pcap"
    wrpcap(str(path), packets)
    return path

def test_detects_tcp_syn_scan(tmp_path):
    pcap = generate_port_scan_pcap(tmp_path)
    from src.detectors.port_scan import detect
    alerts = detect(rdpcap(str(pcap)))
    assert len(alerts) == 1
    assert alerts[0].src_ip == "10.0.0.5"
    assert alerts[0].scan_type == "TCP_SYN_SCAN"
```

### Obstáculos conhecidos

**Scapy exige root/raw sockets.** O container precisa de capabilities especiais (`NET_RAW`, `NET_ADMIN`). No Fly.io, isso é permitido em containers que declaram essas capabilities no Dockerfile. Para captura **live** (interfaces reais), seria necessário o host-level access que o Fly não oferece em planos gerenciados — portanto o projeto sempre trabalha sobre PCAPs fornecidos pelo usuário (arquivo de entrada), não captura live. Isso simplifica o deploy e mantém o projeto dentro do free tier.

**Captura live em container Docker.** Por padrão, um container não vê tráfego da rede do host. Opções:

1. Usar modo `host` networking (simples, mas quebra isolamento)
2. Capturar apenas PCAPs fornecidos pelo usuário (opção escolhida — mais seguro)

**PCAPs grandes.** Limitar upload a 50 MB. Se maior, retornar erro amigável.

**Privacidade em PCAPs de exemplo.** Nunca usar tráfego real. Sempre gerar sintético com Scapy para testes.

## Projeto #3 — Password Manager

**Matéria:** Algoritmos e Estruturas de Dados I
**Impacto:** 🟡 Médio
**Categoria:** Interactive
**Esforço:** 2 semanas

### Objetivo

Gerenciador de senhas zero-knowledge. Três aspectos se reforçam:

1. **Criptografia forte** — Argon2id para derivar chave mestra, AES-256-GCM para criptografar entries
2. **Estrutura de dados** — árvore B+ para organizar entries em memória (aplicação direta de AED I)
3. **Zero-knowledge** — servidor nunca vê dados em claro; tudo acontece no cliente

### Stack

| Camada          | Tecnologia                                             |
| --------------- | ------------------------------------------------------ |
| UI              | Next.js 15 client-heavy                                |
| Crypto          | `@portfolio/crypto-utils` (criar durante este projeto) |
| Storage         | IndexedDB (dexie.js)                                   |
| Sync (opcional) | Backend NestJS com blobs criptografados                |

### Passo a passo

**Semana 1 — Crypto e estrutura**

Dia 1: Criar `@portfolio/crypto-utils` seguindo `docs/workflow/new-package.md`. Funções: `deriveKey` (Argon2id), `encrypt`/`decrypt` (AES-256-GCM), `generateRandom`.

Dia 2-3: Implementar B+ tree com TDD. Testes cobrindo:

- Inserção mantém invariantes (altura balanceada, nós com $\lceil m/2 \rceil \le$ chaves $\le m$)
- Busca em $O(\log n)$
- Remoção com merge/redistribute

Dia 4: `vault.ts` que usa B+ tree para organizar entries e cripto para persistir

Dia 5: Testes de integração — vault criado, entries adicionadas, serialização criptografada, desserialização correta

**Semana 2 — UI e polimento**

Dia 1-2: UI de unlock (formulário de master password)
Dia 3: UI de lista de entries + busca
Dia 4: Gerador de senhas com análise de entropia
Dia 5: Exportação/importação (formato criptografado)
Dia 6: MDX no portfólio com explicação detalhada do zero-knowledge
Dia 7: Deploy + integração

### Critérios de aceite

- [ ] Cobertura ≥ 90% em `src/lib/`
- [ ] B+ tree funciona com `m=4` e `m=100` (testa limites)
- [ ] Tempo de `deriveKey` ≥ 500ms em laptop médio (proteção contra brute force)
- [ ] Análise de entropia alerta para senhas fracas em tempo real
- [ ] MDX explica AES-GCM autenticado e por que não usar AES-CBC
- [ ] Demo interativa funcional com vault temporário (limpo ao fechar aba)

### Obstáculos conhecidos

**Argon2 em browser.** Usar `argon2-browser` (WASM) ou `hash-wasm`. Esperar warm-up de alguns centenas de ms na primeira vez.

**IndexedDB e crypto.** IndexedDB serializa objetos — CryptoKey não é serializável. Armazenar apenas o resultado criptografado como `ArrayBuffer`, re-derivar chave a cada unlock.

**Vault temporário vs persistente.** Para a demo pública, fazer vault apenas em memória (não persistir). Para uso real, salvar em IndexedDB com opção de clear.
