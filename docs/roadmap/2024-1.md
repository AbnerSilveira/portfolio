## Projeto #4 — SQL Injection Scanner

**Matéria:** Banco de Dados I
**Impacto:** 🔴 Alto
**Categoria:** Sandbox
**Esforço:** 2 semanas

### Objetivo

Scanner automatizado de SQL Injection que suporta os 4 tipos principais:

1. **UNION-based** — `id=1 UNION SELECT username, password FROM users`
2. **Error-based** — induz erros SQL que revelam schema
3. **Boolean-based blind** — `id=1 AND 1=1` vs `id=1 AND 1=2`
4. **Time-based blind** — `id=1; IF (...) WAITFOR DELAY '0:0:5'`

Para cada vulnerabilidade encontrada: payload, response, severidade CVSS, remediação sugerida.

### Stack

| Camada            | Tecnologia                    |
| ----------------- | ----------------------------- |
| Crawler/fuzzer    | Python + Playwright + httpx   |
| Motor de detecção | Python puro                   |
| Relatórios        | Jinja2 + HTML                 |
| UI                | Next.js (runner no portfólio) |

### Arquitetura

```
apps/projects/sql-injection-scanner/
├── python/
│   ├── src/
│   │   ├── crawler.py             # Descobre forms e params
│   │   ├── payloads/
│   │   │   ├── union.py
│   │   │   ├── error.py
│   │   │   ├── boolean.py
│   │   │   └── time.py
│   │   ├── detector.py            # Orquestra payloads
│   │   ├── reporter.py            # Gera HTML/JSON
│   │   └── cli.py
│   └── tests/
├── web/                           # UI interativa
├── fixtures/
│   └── dvwa-targets.json          # Lista fechada de alvos sandbox
├── Dockerfile
├── CLAUDE.md
└── README.md
```

### Passo a passo

**Semana 1 — Motor**

Dia 1: Setup Python + Docker Compose local com DVWA (para testar contra alvo real)
Dia 2-3: Payloads UNION e error-based (TDD contra DVWA local)
Dia 4: Boolean-based blind (lógica mais delicada — comparar responses)
Dia 5: Time-based blind (timing attacks precisam tolerância de variação de rede)
Dia 6: Crawler básico descobrindo forms
Dia 7: CLI unificando tudo

**Semana 2 — Sandbox + Portfólio**

Dia 1: Dockerfile hardened para o scanner
Dia 2: Integrar ao `services/sandbox-runner` (ver `docs/architecture/sandbox-security.md`)
Dia 3: Configurar DVWA e Juice Shop como alvos na rede `sandbox-targets`
Dia 4: UI no portfólio — usuário escolhe alvo (enum), vê progresso em tempo real
Dia 5: Relatório HTML estilo Burp
Dia 6: Testes de segurança do sandbox (validar que scanner não consegue escapar)
Dia 7: MDX + deploy

### Restrições críticas de segurança

**Nunca aceitar URL arbitrária.** Só targets pré-configurados:

```typescript
const sqliTargets = z.enum(["dvwa", "juice-shop", "webgoat-sqli"]);
```

**Scanner roda em rede isolada.** `network_mode: sandbox-targets` — só alcança DVWA/Juice Shop, nada mais.

**Rate limit por IP cliente.** Máximo 3 scans/hora por IP. Um scan dura ~60s.

## Projeto #5 — Esteganálise

**Matéria:** Introdução a Visão Computacional
**Impacto:** 🟡 Médio
**Categoria:** Interactive
**Esforço:** 2 semanas

### Objetivo

Ferramenta que detecta mensagens escondidas em imagens via **LSB steganography**. Três métodos:

1. **Análise visual** — extrair só os bits LSB e mostrar como imagem (padrão estrutural denuncia stego)
2. **Chi-squared** — teste estatístico que mede se a distribuição de pares de LSBs está uniforme (sinal de stego)
3. **RS analysis** — Regular/Singular groups, mais sofisticado

### Stack

| Camada        | Tecnologia                                                      |
| ------------- | --------------------------------------------------------------- |
| UI            | Next.js client-heavy                                            |
| Processamento | WebAssembly compilado de Rust (ou Python compilado via Pyodide) |
| Visualização  | Canvas API + D3.js                                              |

### Por que WASM

Análise de imagens 4K tem milhões de pixels. JavaScript puro seria lento demais para interatividade. Rust compilado para WASM dá ~10x speedup.

Alternativa: Pyodide (Python no browser). Pesa 10+ MB só de bootstrap — só vale a pena se reaproveitar código Python existente.

**Decisão:** Rust + `wasm-pack`. Mais leve, mais rápido, aprende-se algo útil.

### Arquitetura

```
apps/projects/stegananalysis/
├── rust/
│   ├── src/
│   │   ├── lib.rs
│   │   ├── lsb_extract.rs
│   │   ├── chi_squared.rs
│   │   └── rs_analysis.rs
│   ├── Cargo.toml
│   └── tests/
├── web/
│   ├── src/
│   │   ├── app/
│   │   ├── components/
│   │   │   ├── ImageUpload.tsx
│   │   │   ├── LSBViewer.tsx
│   │   │   ├── ChiSquaredChart.tsx
│   │   │   └── ResultsPanel.tsx
│   │   └── lib/
│   │       └── wasm-bridge.ts
│   └── ...
├── fixtures/
│   ├── clean-image.png
│   ├── steg-lsb-1bit.png
│   └── steg-lsb-3bit.png
└── ...
```

### Passo a passo

**Semana 1 — Core Rust + WASM**

Dia 1: Setup `cargo`, `wasm-pack`, exportar função hello-world para JS
Dia 2: `lsb_extract.rs` com TDD (usar imagens fixture conhecidas)
Dia 3: `chi_squared.rs`
Dia 4: `rs_analysis.rs`
Dia 5: Integração com Next.js via dynamic import do WASM

**Semana 2 — UI**

Dia 1-2: Upload e preview de imagem
Dia 3: Visualização LSB (Canvas com bits ampliados)
Dia 4: Chart de Chi-squared por bloco
Dia 5: Resultado agregado (veredicto "provavelmente sem stego" / "sinal forte de stego")
Dia 6: MDX explicando o fundamento matemático
Dia 7: Deploy

### Obstáculos

**Tamanho do bundle.** WASM adiciona 100-500 KB. Lazy-load apenas quando o usuário abrir a ferramenta.

**Imagens com compressão lossy (JPEG).** LSB não funciona — JPEG destrói os bits. Rejeitar arquivos JPEG ou avisar o usuário. Aceitar apenas PNG, BMP, TIFF.

## Projeto #6 — OWASP Scanner

**Matéria:** Tecnologia Web
**Impacto:** 🔴 Alto
**Categoria:** Sandbox
**Esforço:** 3 semanas

### Objetivo

Scanner focado em vulnerabilidades do **OWASP Top 10 2021**:

- **A01 — Broken Access Control** (IDOR)
- **A02 — Cryptographic Failures** (HTTPS ausente, certificados)
- **A03 — Injection** (XSS refletido, stored, DOM-based; já cobre SQLi do projeto 4)
- **A05 — Security Misconfiguration** (headers de segurança)
- **A07 — Identification and Authentication Failures** (senhas fracas, lockout)
- **A08 — Software and Data Integrity Failures** (subresource integrity)
- **A10 — Server-Side Request Forgery** (SSRF)

### Stack

| Camada           | Tecnologia           |
| ---------------- | -------------------- |
| Runner           | Node.js + Playwright |
| Engine de regras | TypeScript puro      |
| UI               | Next.js no portfólio |

### Por que 3 semanas

OWASP Scanner é o projeto mais complexo do semestre. Cobrir 7 categorias bem é melhor do que as 10 superficialmente.

**Prioridade:** cobrir A01, A03, A05, A10 muito bem (mais prevalentes em auditorias reais).

### Arquitetura

```
apps/projects/owasp-scanner/
├── src/
│   ├── checks/
│   │   ├── xss-reflected.ts
│   │   ├── xss-stored.ts
│   │   ├── idor.ts
│   │   ├── security-headers.ts
│   │   ├── ssrf.ts
│   │   ├── weak-auth.ts
│   │   └── ...
│   ├── engine.ts                  # Orquestra checks
│   ├── reporter.ts                # Formato OWASP-compatible
│   └── cli.ts
├── tests/
├── fixtures/
│   ├── juice-shop/                # targets para testes
│   └── webgoat/
├── CLAUDE.md
└── README.md
```

### Passo a passo

**Semana 1 — Checks de injection e XSS**

Dia 1: Setup + primeira check (XSS refletido) com TDD
Dia 2-3: XSS stored e DOM-based
Dia 4: IDOR (precisa de múltiplos usuários no DVWA)
Dia 5: Command injection (mais específico, mas complementa)

**Semana 2 — Checks passivos**

Dia 1: Security headers (CSP, HSTS, X-Frame-Options, etc.)
Dia 2: Weak authentication (força bruta com wordlist top 100)
Dia 3: SSRF (payload interno para AWS metadata, etc.)
Dia 4: Cryptographic (detectar HTTP em produção, certs inválidos)
Dia 5: Integrity failures (SRI ausente, CORS permissivo)

**Semana 3 — Relatório + sandbox + polimento**

Dia 1-2: Reporter com export HTML/PDF/JSON
Dia 3: Integração ao sandbox runner
Dia 4: UI no portfólio com escolha de alvo (enum) + visualização de progress
Dia 5: Extrair padrões comuns para `@portfolio/security-validators` (regex de SQLi, XSS, SSRF)
Dia 6: MDX + vídeo demo
Dia 7: Deploy e validação
