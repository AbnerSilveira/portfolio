## Projeto #10 — CIS Auditor ⭐

**Matéria:** Segurança e Auditoria de Sistemas
**Impacto:** 🔴 Alto
**Categoria:** Sandbox
**Esforço:** 3 semanas

**Projeto-âncora.** Demonstra entendimento profissional de compliance. Recrutadores de security corporate reconhecem CIS Benchmarks imediatamente — é o padrão de facto em auditoria.

### Objetivo

Ferramenta que audita configurações de sistema contra **CIS Benchmarks**:

- **CIS Ubuntu 22.04 LTS Benchmark v2.x** — Linux
- **CIS Windows Server 2022 Benchmark v2.x** — Windows (via WinRM/PowerShell remoto)

Gera relatório com:

- Score geral de conformidade (%)
- Lista de controles verificados com status (pass/fail/manual)
- Remediações sugeridas (comandos shell prontos para copy-paste)
- Relatório executivo e técnico (HTML + PDF)

### Escopo realista

CIS Ubuntu tem ~250 controles. Cobrir **80 controles críticos** (Level 1, automatic) é suficiente para projeto acadêmico e já dá relatório impressionante. Escolher os controles mais impactantes de cada seção.

### Stack

| Execução remota    | SSH (paramiko) para Linux, WinRM (pywinrm) para Windows |
| Relatórios         | Jinja2 + WeasyPrint (PDF)                               |

### Modelo de um check

```python
# src/checks/base.py
from dataclasses import dataclass
from enum import Enum
from typing import Callable

class Status(Enum):
    PASS = "pass"
    FAIL = "fail"
    MANUAL = "manual"
    ERROR = "error"

@dataclass
class CheckResult:
    check_id: str
    title: str
    status: Status
    details: str
    remediation: str | None = None

class Check:
    check_id: str
    title: str
    section: str
    level: int
    automated: bool

    def run(self, executor) -> CheckResult:
        raise NotImplementedError
```

Exemplo concreto:

```python
# src/benchmarks/ubuntu_22_04/section_2_services.py
class Disable_AutoFS_v1_1(Check):
    check_id = "1.1.1.2"
    title = "Ensure autofs services are not in use"
    section = "1.1.1"
    level = 1
    automated = True

    def run(self, executor) -> CheckResult:
        result = executor.run("systemctl is-enabled autofs 2>&1 || echo 'not-found'")
        if "not-found" in result.stdout or "masked" in result.stdout:
            return CheckResult(
                check_id=self.check_id,
                title=self.title,
                status=Status.PASS,
                details="autofs is disabled or not installed",
            )
        return CheckResult(
            check_id=self.check_id,
            title=self.title,
            status=Status.FAIL,
            details=f"autofs is: {result.stdout.strip()}",
            remediation="systemctl --now mask autofs",
        )
```

### Passo a passo

**Semana 1 — Motor**

Dia 1: Setup Python + estrutura de checks + SSH executor com paramiko
Dia 2-3: 15 checks da seção 1 (Initial Setup) com TDD contra container Ubuntu local
Dia 4-5: 25 checks de seções 2-4 (Services, Network, Logging)
Dia 6-7: 40 checks restantes (Access, Maintenance)

**Semana 2 — Relatórios**

Dia 1: Jinja2 template HTML estilo CIS-CAT
Dia 2: WeasyPrint para PDF
Dia 3: Score calculation (weighted por severidade)
Dia 4: Relatório executivo (1 página) vs técnico (detalhado)
Dia 5: Remediation scripts — gerar bash script com todos os fixes
Dia 6-7: Suporte Windows (pywinrm + checks Windows Server)

**Semana 3 — Sandbox + UI**

Dia 1-2: Imagem Docker Ubuntu 22.04 "sacrificial" — o sandbox runner (no Fly.io) spawna um container efêmero dessa imagem para cada audit, roda o auditor dentro, captura relatório, destrói o container
Dia 3: Sandbox runner aceita `cis-auditor` como projeto — usuário dispara audit
Dia 4: UI no portfólio — progresso em tempo real, resultado em cards
Dia 5: Download de relatório PDF
Dia 6: MDX com explicação de CIS Benchmarks
Dia 7: Deploy + validação

### Integração vitrine

## Projeto #11 — Mobile 2FA

**Matéria:** Aplicativos Mobile
**Impacto:** 🟡 Médio
**Categoria:** Interactive + APK
**Esforço:** 3 semanas

### Objetivo

App mobile que:

1. **Gera códigos TOTP** (RFC 6238) — estilo Google Authenticator
2. **Backup criptografado** — export para arquivo `.age` protegido por senha
3. **Scanner de permissões perigosas** (apenas Android) — lista apps instalados e classifica risco das permissões

### Stack decisão

**Flutter** ou **React Native**? Requisito: precisa acessar API nativa do Android para listar apps instalados.

- Flutter: plugin `device_apps` permite listar apps. Mais maduro.
- RN: `react-native-installed-apps-launcher`. Menos mantido.

**Decisão:** Flutter. Também é oportunidade de adicionar Dart ao portfólio (linguagem diferente das 5 que já estão no portfólio — Python, TS, JS, Rust, SQL).

### Stack

| Camada    | Tecnologia               |
| --------- | ------------------------ |
| Framework | Flutter 3.x              |
| Crypto    | `cryptography` do Dart   |
| Storage   | `flutter_secure_storage` |
| Packaging | APK assinado + AAB       |

### Passo a passo

**Semana 1 — TOTP core**

Dia 1: Setup Flutter + primeiro widget
Dia 2-3: Implementação RFC 6238 do zero (TDD com vetores oficiais do RFC)
Dia 4: UI de lista de contas 2FA
Dia 5: QR code scanner para adicionar contas (`mobile_scanner`)
Dia 6: Timer animado dos 30 segundos
Dia 7: Armazenamento criptografado em `flutter_secure_storage`

**Semana 2 — Backup + Scanner de permissões**

Dia 1-2: Exportação de backup — arquivo criptografado com senha (AES-256-GCM + Argon2)
Dia 3: Importação e validação
Dia 4-5: Scanner de apps instalados (Android-only)
Dia 6: Classificação de risco das permissões (high: SMS/location/contacts; low: internet)
Dia 7: UI do scanner com filtros

**Semana 3 — Polimento e distribuição**

Dia 1: Dark mode, acessibilidade
Dia 2-3: Gerar APK assinado + instruções de sideload
Dia 4: Opcionalmente, submeter para F-Droid (acadêmico)
Dia 5: Criar página web (Next.js) com preview dos screens + download do APK
Dia 6: MDX no portfólio
Dia 7: Vídeo demo rodando no device real

### Observações

App store oficial (Play/App Store) são cara demais para projeto acadêmico ($25 Play, $99/ano Apple). APK assinado + sideload é suficiente para demonstrar o projeto no portfólio.

## Projeto #12 — DevSecOps Pipeline

**Matéria:** Gestão da Qualidade de Software
**Impacto:** 🟢 Pequeno
**Categoria:** Documentation + live CI
**Esforço:** 1 semana

### Objetivo

Documentar + evoluir o pipeline DevSecOps já existente no próprio monorepo. Adicionar:

- **DAST** com OWASP ZAP em automation mode contra o portfólio em staging
- **Container scanning** com Trivy
- **SBOM generation** com syft
- **Runtime monitoring** com Falco rodando na Fly Machine do sandbox runner (detectar processos suspeitos dentro dos containers efêmeros). Na temporada do honeypot, Falco também roda na Hetzner.

### Por que 1 semana só

Projeto é mais documentação que código. O pipeline já existe desde a Fase 0. Aqui é evolução + redação.

### Passo a passo

**Dia 1:** Adicionar ZAP no pipeline

```yaml
# .github/workflows/dast.yml
name: DAST
on:
  schedule:
    - cron: "0 3 * * 0" # Domingo 3h UTC
jobs:
  zap-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: zaproxy/action-baseline@v0.13.0
        with:
          target: ${{ secrets.STAGING_URL }}
```

**Dia 2:** Trivy para scan de imagens antes do deploy
**Dia 3:** Syft gerando SBOM em cada release
**Dia 4:** Falco no Fly Machine do sandbox runner + webhook para Slack quando detectar eventos
**Dia 5-6:** MDX completo no portfólio — arquitetura do pipeline, o que cada etapa faz, links para workflows reais no GitHub
**Dia 7:** Criar "status page" no portfólio — widget mostrando último build, último DAST, última auditoria do honeypot
