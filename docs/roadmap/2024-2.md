## Projeto #7 — Honeypot ⭐

**Matéria:** Sistemas Operacionais
**Impacto:** 🔴 Alto
**Categoria:** Híbrida (dashboard live + vídeo)
**Esforço:** 3 semanas

**Projeto-hero.** Vale investimento extra de polimento. É o primeiro projeto do portfólio que roda com **dados reais acumulados** em produção — um dos maiores diferenciais possíveis.

### Objetivo

Honeypot multi-serviço que simula SSH, FTP e HTTP vulneráveis. Captura:

- Credenciais tentadas (login/password)
- Comandos executados após "login" bem-sucedido
- Payloads enviados (downloads de malware, etc.)
- User-agents, IPs, fingerprints TLS

Dashboard exibe ataques em tempo real com enriquecimento (geolocalização, reputação do IP via AbuseIPDB).

### Stack

| Camada         | Tecnologia                                |
| -------------- | ----------------------------------------- |
| Simuladores    | Python (SSH via paramiko-like, FTP, HTTP) |
| Armazenamento  | PostgreSQL                                |
| Backend API    | NestJS                                    |
| Dashboard      | Next.js + Recharts + mapa (leaflet.js)    |
| Enriquecimento | `services/threat-intel-aggregator`        |

### Conformidade LGPD

IPs de atacantes são dados pessoais sob LGPD. Base legal: **legítimo interesse** (Art. 7º, IX) — honeypot é sistema de segurança.

Mitigações obrigatórias:

- Retenção máxima: 90 dias
- Exibição pública do dashboard: mascarar últimos octetos (`1.2.3.xxx`)
- Nunca publicar IPs completos em MDX ou logs públicos
- Política de privacidade do portfólio menciona o honeypot e sua base legal

### Passo a passo

**Semana 1 — Simuladores**

Dia 1: Setup Python. SSH honeypot básico (aceita qualquer login, loga credenciais)
Dia 2: Fake shell — responde a `ls`, `whoami`, `cat /etc/passwd` com conteúdo fake plausível
Dia 3: FTP honeypot
Dia 4: HTTP honeypot — rotas `/phpmyadmin/`, `/wp-login.php`, `/admin/` capturando tentativas
Dia 5: Schema PostgreSQL + gravação de ataques com Prisma (DB = branch `honeypot-capture` no Neon)
Dia 6: Dockerizar cada simulador
Dia 7: **Início da temporada Hetzner** — provisionar VPS pelo script em `infra/hetzner-temporada/`, deploy com Docker Compose, DNS `honeypot.<dominio>` apontando pro IP novo. A VPS ficará ativa por ~3 meses coletando dados reais.

**Semana 2 — Backend e enriquecimento**

Dia 1-2: `services/threat-intel-aggregator` criado (ver subseção abaixo)
Dia 3: NestJS API para o dashboard (REST + WebSocket para stream live)
Dia 4: Worker de enriquecimento (job Bull/Redis que processa ataques novos)
Dia 5: Auth simples no dashboard (basic auth para área interna)
Dia 6: Endpoint público de stats agregadas (sem IPs identificáveis)
Dia 7: Testes e hardening

**Semana 3 — Dashboard + polimento**

Dia 1-2: AttackFeed com WebSocket
Dia 3: GeoMap com Leaflet.js
Dia 4: Top N de credenciais, comandos e ASNs
Dia 5: Embed no portfólio público
Dia 6: Gravação de vídeo explicativo
Dia 7: MDX + deploy final

### `services/threat-intel-aggregator`

Criar durante esta semana — é usado pelo honeypot e depois pelo Threat Intel Dashboard (#14).

```
services/threat-intel-aggregator/
├── src/
│   ├── providers/
│   │   ├── abuseipdb.ts
│   │   ├── virustotal.ts
│   │   ├── shodan.ts
│   │   └── otx.ts                 # AlienVault OTX (free tier generoso)
│   ├── cache.ts                   # Redis — evitar gastar rate limits
│   ├── aggregator.ts
│   └── api.ts
└── ...
```

**Rate limits críticos:**

- AbuseIPDB: 1000 requests/dia (free)
- VirusTotal: 500/dia
- Shodan: depende de API key (pagar plano básico ~$49/ano se valer a pena)

Cachear agressivamente no Redis. TTL de 24h.

## Projeto #8 — Encrypted Storage

**Matéria:** Banco de Dados II
**Impacto:** 🔴 Alto
**Categoria:** Interactive
**Esforço:** 2 semanas

### Objetivo

Sistema de criptografia de dados em repouso com:

- Criptografia por coluna (`pgcrypto` no Postgres)
- Rotação de chaves (KMS simplificado)
- **Detector de PII** — escaneia campos texto e identifica CPF, CNPJ, RG, email, cartão de crédito (com validação Luhn)

### Stack

| Camada       | Tecnologia                              |
| ------------ | --------------------------------------- |
| Backend      | NestJS + Prisma + Postgres pgcrypto     |
| KMS          | Serviço simples com master key rotativa |
| Detector PII | Regex + validações algorítmicas         |
| UI           | Next.js                                 |

### Arquitetura

```
apps/projects/encrypted-storage/
├── backend/
│   ├── src/
│   │   ├── modules/
│   │   │   ├── kms/
│   │   │   │   ├── key-rotation.service.ts
│   │   │   │   └── master-key.service.ts
│   │   │   ├── storage/
│   │   │   │   ├── encrypted-record.entity.ts
│   │   │   │   └── storage.service.ts
│   │   │   └── pii-detector/
│   │   │       ├── detectors/
│   │   │       │   ├── cpf.ts
│   │   │       │   ├── cnpj.ts
│   │   │       │   ├── credit-card.ts
│   │   │       │   └── email.ts
│   │   │       └── pii-detector.service.ts
│   │   └── ...
├── web/                           # UI interativa
│   └── ...
├── CLAUDE.md
└── README.md
```

### Passo a passo

**Semana 1 — Core**

Dia 1: Setup NestJS + Prisma + pgcrypto habilitado
Dia 2: KMS simples — chave mestra em env, chaves de dados derivadas, rotação por versão
Dia 3: CRUD com criptografia transparente (decorator Prisma)
Dia 4-5: Detector de PII com TDD

- CPF: validação DV
- CNPJ: validação DV
- Cartão: Luhn
- Email: regex + validação DNS opcional
- RG: regex variável por estado (limitar a SP)
  Dia 6-7: Testes de integração e cobertura

**Semana 2 — UI + polimento**

Dia 1-2: UI de upload de texto, destacar PII detectado
Dia 3: UI de CRUD de entries com campo marcado como "sensível"
Dia 4: Demo de rotação de chave (usuário vê dados sendo re-encriptados)
Dia 5-6: MDX explicando pgcrypto + detecção de PII
Dia 7: Deploy

### Uso de `@portfolio/crypto-utils`

Já existe desde o projeto 3. Estender com helpers de KMS se ainda não tiver.

## Projeto #9 — WAF

**Matéria:** Sistemas Web
**Impacto:** 🔴 Alto
**Categoria:** Sandbox
**Esforço:** 3 semanas

### Objetivo

Web Application Firewall posicionável como **middleware Express/Fastify**. Engine de regras:

- Rate limiting por IP/rota
- Bloqueio por padrões (SQLi, XSS, Command Injection, Path Traversal)
- Bloqueio por reputação (integra `threat-intel-aggregator`)
- Virtual patching — regras declarativas em YAML

Dashboard em tempo real mostra requests bloqueados/permitidos.

### Stack

| Camada     | Tecnologia                |
| ---------- | ------------------------- |
| Engine     | Node.js + TypeScript puro |
| Rate limit | Redis                     |
| Dashboard  | Next.js + WebSocket       |
| Config     | YAML                      |

### Arquitetura

```
apps/projects/waf/
├── engine/                        # O middleware
│   ├── src/
│   │   ├── rules/
│   │   │   ├── sqli.ts
│   │   │   ├── xss.ts
│   │   │   ├── command-injection.ts
│   │   │   ├── path-traversal.ts
│   │   │   └── scanner-detection.ts
│   │   ├── rate-limit.ts
│   │   ├── reputation.ts
│   │   ├── config-loader.ts
│   │   ├── middleware.ts
│   │   └── events.ts              # Emit para dashboard
│   ├── tests/
│   └── package.json
├── dashboard/                     # UI
│   └── ...
├── demo-target/                   # App vulnerável protegida pelo WAF (demo)
│   └── ...
├── config/
│   └── default.yaml
└── ...
```

### Passo a passo

**Semana 1 — Engine**

Dia 1: Setup + middleware que loga todas requests
Dia 2-3: Regras de SQLi e XSS (reutilizar `@portfolio/security-validators`)
Dia 4: Command injection, path traversal
Dia 5: Rate limit com Redis (token bucket)
Dia 6-7: Virtual patching — carregar regras de YAML

**Semana 2 — Reputação e eventos**

Dia 1-2: Integração com `threat-intel-aggregator` — bloquear IPs com score alto
Dia 3: Event emitter (todas decisões do WAF viram eventos)
Dia 4: WebSocket server para dashboard
Dia 5-7: Testes de integração — montar app Express, aplicar middleware, testar cenários

**Semana 3 — Dashboard + sandbox**

Dia 1-2: Dashboard com stream em tempo real
Dia 3: Gráficos — requests/s, taxa de bloqueio, top IPs bloqueados
Dia 4: Demo target (pequena app vulnerável) rodando atrás do WAF
Dia 5: Sandbox — usuário tenta ataques no demo target, vê WAF bloqueando
Dia 6: MDX
Dia 7: Deploy
